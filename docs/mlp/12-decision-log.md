| S1-1 | 2026-09-28 | **Offline-first with one shared engine.** Every user or capture action is a *command* whose logic lives once in `@zeta/shared`. The phone runs it immediately against local SQLite (full result offline: dedup, merchant, category, bills, balances, Te deben) and queues the command, not the rows. The server replays the same command with the same code against Postgres (plus what only it sees: Gmail, PDF) and records the command id so replays are idempotent. Sync brings the server's result back. One test suite runs every command against both storage adapters. Cost: +2–3 weeks in M0/M1. Needs signal only for: Gmail capture, PDF parsing, naming never-seen merchants, template pack updates, detail older than the local window, new-device sign-in. | `10-build-plan.md` §2 "captures go through `/api/ingest`, phone shows pendiente" |
| S1-2 | 2026-09-28 | **Conflicts split by kind of field.** Bank facts (amount, date, merchant text): higher capture tier wins (PDF › email › notification › manual). User choices (category, note, split/share, cuotas, trip, bill link): the user's value always survives a server replay; same field edited on two devices → latest edit wins (per-field timestamp). Weak duplicate matches are never auto-resolved; they become a Revisar card. | — |
| S1-3 | 2026-09-28 | **History on the phone = last 3 cycles of movements + one summary per closed cycle, forever.** Summary contents: four lines + adjustments + result + verdict at close; income (salary / other / repayments) vs total out; spending by category (amount, share, count) + top 5 merchants; start/end balance per account + liquid total; end balance per card/loan, pending cuotas, interest and fees; Te deben / Tú debes open at close; each límite (spent vs limit, verdict); savings + surplus decision. | S3-0 | 2026-09-29 | **Owner correction — credit cards and counted accounts.** A card's available credit is never Disponible. Card purchases do not lower Disponible when made (they lower the card's available credit); the **card bill** enters Por pagar in the pay cycle it's due, projected from seen purchases + cuotas + estimated interest until the PDF gives the exact amount; paying it moves Por pagar → Ya salió (label "Pago de tarjeta", not a spending category). Paying a card before its bill exists lowers Disponible now and the next bill later. **The user chooses which accounts count for Disponible** (default: checking, savings, cash; investments no; cards/loans never). Transfers between counted accounts: no effect; counted → not counted: down (fills the cycle's Ahorro first); not counted → counted: up. Schema: new side table `account_settings (account_id PK, counts_in_disponible)` (avoids `accounts_enc` column) — 14th new table. | `03-experience-proposal.md` §7 "card purchases count when you buy"; `10-build-plan.md` §4.1 `cardPurchasesAlreadyCounted` |
