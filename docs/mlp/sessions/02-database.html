Zeta v2 · Planning session 2 of 6

Zeta v2's database

What's in the database today, what v2 keeps, adds and stops using, and why. Also how encryption works, what the phone stores, and how changes reach the database without breaking the web app you still use. Four decisions at the end.

The short version

Mostly reuse

Today's database already models almost everything v2 needs: accounts including loans, movements, merchants and people, bills and their due dates, Te deben and Tú debes, límites and trips. Most of v2's data work is new rules, not new tables.

Nothing breaks

Every change until v2 ships is additive (S1-4): new tables and new columns only. The web app and today's mobile app keep working on the same data. Tables v2 stops using are frozen, not deleted.

13 new tables

10 for features (command log, cycle summaries, pay schedule, merchant policy, split bill payments, 2 for notification templates, source health, Gmail link, push tokens) and 3 support tables (per-field versions, category mapping, merchant-name cache).

How encryption works, from the server to your phone

How the database gets created and changed

For a new user

  • Sign-in creates the account (Supabase Auth)
  • A database trigger creates your profile and your own encryption key
  • The 25 categories are shared system rows (nothing to copy)
  • Onboarding writes your pay schedule and first balance, as commands
  • The phone creates its local database on first launch and pulls your data

For every schema change

  • Written as a migration file in supabase/migrations/ (163 so far)
  • Reviewed by the supabase-migrator agent; mandatory for 🔒 tables
  • Applied to the dev project first (S1-5), with the command tests run against it
  • Applied to production by hand (supabase db push): deploys don't run migrations
  • Additive only until v2 ships (S1-4)
  • The phone's database has its own numbered migrations, run at app start

Decisions for this session

S2-1

Encrypt the phone's database file?

The phone holds your merchants, notes and raw bank notification text in plain form, so it can work offline.

RECOMMENDEDYes, with SQLCipherThe whole file is encrypted; its key lives in the iPhone Keychain / Android Keystore. It's supported by expo-sqlite with one config flag. Cost: about 5–15% slower queries (unnoticeable at this size), and the local database starts fresh once (it re-syncs).
No, rely on the phone's own protectioniOS and Android already encrypt storage while the phone is locked, and Face ID app lock exists. That's weaker on rooted phones and in device backups.
S2-2

How long do we keep the details of each command?

A command's id must be kept forever (so a late resend is never applied twice). Its details (what you did, with names and amounts) are only needed for replays, debugging and "undo".

RECOMMENDEDDetails for 90 days, id foreverEnough for any offline gap, debugging and undo. After 90 days, only the id, type and date remain. The details are encrypted with your key while kept.
Keep everything foreverA complete history of every change you made. It could power a future "historial de cambios", but it's more personal data stored indefinitely.
S2-3

Moving existing users to the 25 categories

RECOMMENDEDProposed, one tap to acceptOn first launch, a card shows the mapping ("Comida rápida → Restaurantes y café", …) with [Usar las 25] and [Mantener las mías]. If accepted, movements are recategorized; your own extra categories remain. The web keeps showing the old ones until then.
AutomaticEveryone moves on day one. Simpler, but people who carefully built categories lose them without being asked.
S2-4

What happens to frozen tables after v2 ships?

RECOMMENDEDKeep 6 months, then export and dropOnce the web is reduced (S1-4), frozen data stays 6 months in case something is missed. Then each user's frozen data is exported (downloadable from Ajustes) and the tables are dropped. Tags stay until D4's update is decided.
Keep foreverNo risk of losing anything, but 18 tables nobody uses stay in every migration and review.
