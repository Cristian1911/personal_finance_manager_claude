How Zeta v2 works

This session covers where each part of Zeta runs, how a purchase gets from your bank to your Disponible, and what works without signal. The answer to that last one is almost everything. The page ends with the decisions for this session. We'll take them one at a time in the chat.

The one rule

The phone decides now; the server confirms with the same code. Everything you do becomes a command ("capture this purchase", "Rappi is always Domicilios", "split with Juan", "pay the loan"). The phone runs it immediately against its own database, and you see the final result offline. The command is queued and the server replays it with the identical code when there's signal.

Why this and not "the server decides": being usable offline is a core premise. The old app's bugs didn't come from the phone making decisions. They came from the phone running a separately written copy of the web's logic, and the two drifted apart (8 data bugs in the 2026-06-25 audit). Here the logic lives once, in @zeta/shared, and both sides run that same code.

How a command works

Why queue commands, not rows

A row says "the table looks like this". A command says "this is what the person did". The server can only redo the work correctly (dedup against data the phone never saw, update the right balances) if it knows the intent. Each command carries its own id, so sending it twice never applies it twice.

Why this fixes the old parity bugs

One test suite runs every command against both storage adapters, SQLite for the phone and Postgres for the server. "The phone and server disagree" becomes a failing test before release, not a wrong number in production.

Decisions for this session

S1-1

Should the phone keep its own copy and work offline?

DECIDED Yes, the phone keeps a local copy and runs the full engine offline. Commands are queued and the server replays them with the same code. Extra cost: about +2 to 3 weeks in M0/M1 to turn the email webhook's inline pipeline into shared commands with SQLite and Postgres adapters.

S1-2

When the server's result differs from the phone's, who wins?

DECIDED Split by kind of field. Bank facts (amount, date, merchant text): the higher-trust source wins (PDF › email › notification › manual). Your choices (category, note, split, cuotas, trip, bill link): yours always win; the same field changed on two devices, the latest change wins. Real doubt (a weak duplicate match) is never decided silently: it becomes a Revisar card.

S1-3

How much history lives on the phone?

DECIDED Last 3 cycles of detail + a summary of every closed cycle, forever. Summaries (about 2–5 KB each) hold: the four lines, adjustments, result and verdict; income (salary, other, repayments) vs total out; spending by category (amount, share, count) and top 5 merchants; starting and ending balance per account; ending debt per card and loan, pending cuotas, interest and fees; Te deben and Tú debes open at close; each límite's result; savings and the surplus decision. Summaries are derived, rebuilt by the same engine when late data arrives (marked "actualizado con el extracto"), and backfilled for existing users. Stored per cycle; the month view adds up its cycles. Only older movement detail needs signal.

S1-4

What does the web app do?

DECIDED Until v2 ships: the current web app stays exactly as it is and in daily use, on the same database. Schema changes are additive only (no renames, drops or meaning changes); v2's server engine is added as new API routes in the same Next.js app; the web gets one small change (the NOTIFICATION capture tier); the email pipeline refactor must replay the saved email corpus with identical results. Expected difference: shared purchases show different spending in each app (web: amount minus repaid; v2: your share). After v2 ships: the web shrinks to PDF bulk import + accounts, running the same commands.

S1-5

Where is v2 developed?

DECIDED A separate Supabase dev project with demo data. Migrations and command code are proven there first; your real account moves to v2 builds only when a milestone is stable.
